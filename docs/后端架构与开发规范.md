# 后端架构与开发规范

> 适用范围：`src/main/java/com/example/zhihuiqingtu`
> 最后更新：2026-11-20

## 1. 设计目标

- **按业务域组织代码**：同一业务的概念（Controller / Service / Entity / Repository / DTO / VO / Enum）放在同一个域包内，避免“改一个功能要在六个顶层目录里来回跳”。
- **依赖方向单一**：`Controller → Service → Repository`，领域之间通过服务或只读仓库协作，`admin` 只作为交付通道，不反向被领域依赖。
- **写操作集中**：事务、权限、状态机、缓存失效都收敛在 Service 层；Controller 只做参数校验与响应封装。
- **可审计**：身份来自 JWT（`CurrentUser` / `AdminGuard`），AI 不直接写业务表，所有关键写操作可追溯到操作者与时间。

## 2. 分层职责

| 层 | 位置 | 职责 | 禁止 |
|---|---|---|---|
| Controller | `<domain>/controller`、`admin/<domain>/controller` | 路由、`@Valid` 入参校验、调用 Service、返回 `ApiResponse` | 写业务逻辑、直接访问 Repository |
| Service | `<domain>/service` + `service/impl` | 业务规则、权限校验、事务、缓存/事件编排 | 直接处理 HTTP 细节 |
| Repository | `<domain>/repository` | 单表/条件 SQL（MyBatis-Plus Mapper） | 业务判断、跨表事务编排 |
| Entity | `<domain>/entity` | 表映射，统一继承 `common.entity.BaseEntity` | 作为接口出入参 |
| DTO / VO | `<domain>/dto`、`<domain>/vo` | 请求/响应模型 | 直接暴露实体 |
| Support | `<domain>/support` | 缓存、库存、热门榜、装配器、发放工厂等可复用能力 | 反向依赖 Controller |

### 3.1 域内结构约定

```text
<domain>/
├── controller/        # 客户端或管理端 HTTP 入口
├── service/           # 接口
│   └── impl/          # 实现
├── repository/        # Mapper 接口
├── entity/            # 表实体
├── dto/               # 入参（XxxRequest / XxxQueryRequest）
├── vo/                # 出参（XxxResponse / XxxVO）
├── enums/             # 本域状态/类型枚举
└── support/           # 可复用支撑能力（缓存/装配/工厂）
```

## 4. 领域职责说明

| 域 | 核心职责 | 主要表 |
|---|---|---|
| `auth` | 注册、登录、登出、JWT 签发与黑名单 | `user_info` |
| `user` | 资料、兴趣标签、个人学分总览、角色/账号状态 | `user_info`、`user_interest_rel` |
| `activity` | 活动发布（客户端/运营/管理员）、审核状态机、列表/详情、标签、档位、库存/缓存/热门榜 | `activity_main`、`activity_tag`、`activity_tag_rel`、`activity_credit_tier` |
| `enrollment` | 报名、取消、自助签到/签退、评价、我的报名 | `activity_enroll` |
| `award` | 活动参与人员、考勤修正、学分/志愿时长发放与批量审核、学分统计、AI 批量导入 | `credit_record` |
| `team` | 建队、加入审核、退出、解散 | `team_main`、`team_member` |

| `admin` | 管理端接口：活动审核、账号管理、概览、运营发布、发放导入 | 复用各域表 |
| `ai` | 对话/推荐/工具/待确认动作、表格列识别 | `ai_*` |

## 5. 依赖规则

1. **`admin` 依赖领域，领域不依赖 `admin`**。管理端使用独立的 Controller/Service/DTO/VO，复用领域服务或只读仓库。
2. **`ai` 是平台能力**：领域可以调用 AI 的列识别等能力；AI 工具不得直接写业务表，写操作必须先登记 `AiPendingAction`，由用户确认后走既有 Service。
3. **跨域写操作经由拥有该数据的服务**；跨域只读查询允许使用目标域 Repository（如活动审核读取报名数量），但不允许在 A 域直接修改 B 域的表。
4. **Controller 不直接注入 Repository**；管理端 Service 允许组合多个域的 Repository 完成查询。
5. **实体不跨层**：Controller 的入参/出参必须是 DTO/VO，不直接暴露 Entity。

## 6. 关键拆分说明

为了让原本 1000+ 行的服务可维护，采用「门面 + 专注服务」模式，对外接口保持不变：

### Activity 域

```text
ActivityController / AdminActivityService
        │
        ▼
ActivityService（稳定门面：对外契约不变）
        ├── ActivityServiceImpl（命令：发布、编辑、状态、签到开关、删除、校验）
        └── ActivityQueryService（只读：列表、详情、标签、热门、剩余名额）
                    └── ActivityAssembler（实体 + 标签 + 档位 → ActivityResponse）
```

- 查询与缓存装配已从 `ActivityServiceImpl` 拆出；
- `ActivityServiceImpl` 保留写路径与发布校验，后续如需继续瘦身，可再把校验抽成 `ActivityPublishValidator`。

### Enrollment / Award 域

```text
EnrollmentController
        │
        ▼
EnrollmentService（稳定门面）
        ├── EnrollmentServiceImpl（报名、取消、查询、签到/签退、评价）
        └── ParticipantAwardService（参与人员、考勤修正、发放、批量确认）
                    └── AwardRecordFactory（签退后生成待确认发放记录）
```

- 自助签到/签退仍属于报名域；发布者/管理员的考勤修正与发放属于 `award` 域；
- 两条签退路径（学生自助、管理员补签退）共用 `AwardRecordFactory`，避免发放规则分叉。

## 7. 命名规范

| 类型 | 规范 | 示例 |
|---|---|---|
| 控制器 | `XxxController` | `EnrollmentController` |
| 服务接口/实现 | `XxxService` / `XxxServiceImpl` | `AwardService` / `AwardServiceImpl` |
| 查询/命令拆分 | `XxxQueryService` / `XxxCommandService` | `ActivityQueryService` |
| 仓库 | `XxxRepository` | `CreditRecordRepository` |
| 实体 | `Xxx`，继承 `BaseEntity` | `ActivityEnroll` |
| 入参 | `XxxRequest` / `XxxQueryRequest` | `UpdateAwardRequest` |
| 出参 | `XxxResponse` / `XxxVO` | `EnrollmentResponse`、`ActivityParticipantVO` |
| 枚举 | `XxxEnum` | `AwardStatusEnum` |
| 管理端 | `AdminXxx...`，放在 `admin/<domain>/` | `AdminReviewActivityRequest` |

命名注意：

- 活动审核状态使用 `ReviewStatusEnum`（0 待审核 / 1 通过 / 2 驳回）；发放状态使用 `AwardStatusEnum`（0 待确认 / 1 已发放 / 2 不发放 / 3 待管理员审核），两者不要混用。
- 身份字段不在请求体中传递，统一由 `CurrentUser`/`AdminGuard` 从 JWT 读取。

## 8. 开发约定

### 8.1 权限

- 客户端：`CurrentUser.requireUserId()`，归属校验在 Service 内完成。
- 管理端：`AdminGuard.requireAdmin()` / `requireStaff()` / `requireStaffOrAdmin()`，每次请求回查数据库角色，防止旧 JWT 携带已降级角色。
- 新 URL 模式需在 `SecurityConfig` 中显式声明；管理端统一放在 `/api/admin/**`。

### 8.2 事务

- 写操作加 `@Transactional(rollbackFor = Exception.class)`；
- Redis/缓存/榜单的变更放到 `TransactionEvents.afterCommit`，回滚时补偿；
- Repository 的自定义 SQL 要自己补 `delete_flag = 0`（MyBatis-Plus 只对内置方法自动加）。

### 8.3 缓存

- 活动详情使用 Cache-Aside，缓存“事实”（状态 + 结束时间），不缓存随时间变化的结论（`displayStatus` 每次现算）；
- 所有写路径在提交后调用 `ActivityCacheService.evict`；
- 报名名额：Redis 是性能闸门，数据库条件 UPDATE 才是正确性保证。

### 8.4 错误与响应

- 业务错误抛 `BusinessException(ErrorCode, message)`，由 `GlobalExceptionHandler` 统一转 `ApiResponse`；
- 成功统一返回 `ApiResponse.success(...)`；分页统一 `PageResponse`。

## 9. 新增一个业务模块的步骤

1. 在 `src/main/java/.../<domain>` 下建 `controller/service/impl/repository/entity/dto/vo/enums`。
2. 实体继承 `BaseEntity`，Mapper 继承 `BaseMapper`，并在启动类 `@MapperScan` 中登记 `repository` 包（新域才需要）。
3. 定义 DTO（Jakarta Validation）与 VO，不直接暴露 Entity。
4. Service 内完成权限、事务、状态机；Controller 只做路由与 `@Valid`。
5. 如需管理端入口，在 `admin/<domain>` 下新增 `AdminXxxController/Service`，复用领域服务或只读仓库。
6. 新增 URL 模式时更新 `SecurityConfig`；新增写操作时补充 `TransactionEvents`/缓存失效。
7. 补充单元测试（Mockito 手动构造风格），运行 `./mvnw test` 全量回归。
8. 更新 `docs/接口文档.md`；涉及表结构时新增 `docs/sql/` 迁移并在 `Mysql.sql` 同步。

## 11. 测试与运行

```bash
./mvnw test                                   # 全量单元/切片测试
./mvnw -q -DskipTests compile                 # 仅编译主代码
./mvnw spring-boot:run -Dspring-boot.run.profiles=local
cd frontend_v2 && npm run dev                 # 客户端 5173
cd frontend_admin && npm run dev              # 管理端 5174
```

- 单测使用 Mockito 手动构造（不启动 Spring），需要 Lambda 条件构造器的测试在 `@BeforeAll` 初始化 MyBatis-Plus 元数据。
- 切片测试（`@WebMvcTest`）用于验证 `SecurityConfig` 放行规则，不能替代权限的服务层测试。
