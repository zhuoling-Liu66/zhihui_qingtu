## 1. 这个项目是干什么的

**一句话：一个校园活动的"发布 → 审核 → 报名 → 签到/签退 → 发放学分或志愿时长 → 组队"全流程管理平台。**

想象一个真实场景：

1. 学生、老师或运营人员在平台上发布活动；**管理员发布的活动免审核直接公开**，其他人发布的活动先进入待审核队列，由管理员审核。
2. **学生**在活动列表里看到它，点"报名"。人数满了就报不上了。
3. 活动进行中，主办方开启"签到开关"，报了名的学生先点**签到**，活动结束时再点**签退**。
4. 签退成功后，系统**自动生成一条"待确认"的发放记录**：第二课堂活动记学分（组合模式先占位），志愿活动记时长（灵活模式先留空）。
5. **活动发布者**在参与人员名单里按人调整金额并确认发放（同一活动不同参与者可以不同）：
   - 学分支持**固定模式**（统一金额）与**组合模式**（如 1 学分 3 名、0.5 学分 20 名，发放时选档位且名额受限）；
   - 志愿时长支持**固定模式**与**灵活模式**（活动结束后逐人录入，提交管理员审核通过才计入统计）。
6. **管理员**拥有同样的权限，可随时修正考勤与发放。

### AI 批量导入发放

发布者可在「参与人员」页使用 **AI 智能导入**：上传 Excel/CSV 后，AI 自动识别表头与“学号/姓名/时长或学分”列（无模型时用规则识别），学号优先、姓名兜底匹配已签退的参与者，预览确认后一键保存。

- 导入记录统一进入「待审核」（`verify_status=3`），运营不能自行通过；
- 管理员可在同一页「一键通过待审核」，通过后计入统计；
- 组合学分按档位名额校验；志愿时长支持“分钟”列自动换算为小时。
6. 学生还能**组队**参加（比如团队赛），队长招募、审核队员、满员或解散。

### 业务域划分

代码按业务域分成了 6 块，每块一个 Controller：

| 业务域 | 干什么 | 入口 |
|---|---|---|
| **认证** | 注册、登录、发 JWT 令牌 | `/api/auth` |
| **用户** | 个人资料、兴趣标签、参与历史、学分总览 | `/api/users` |
| **活动** | 发布、修改、上下架、封面上传、列表查询、标签 | `/api/activities` |
| **报名** | 报名、取消、签到/签退、评价、参与人员与发放管理 | `/api/enrollments` |
| **学分** | 发放记录查询、学分与志愿时长统计 | `/api/credits` |
| **组队** | 建队、加入申请、审核、退出、解散 | `/api/teams` |

一共 **34 个接口**（认证 3 + 用户 5 + 活动 11 + 报名 5 + 学分 3 + 组队 7）。
（原本 31 个；2026-09-20 的 Redis 改造新增了 `/api/auth/logout`、`/api/activities/hot`、
`/api/activities/{id}/stock` 三个。）

## 2. 技术栈：每个库到底负责什么

初学者最容易迷糊的是"这么多依赖，到底谁管什么"。这张表按**职责**排，不按 pom 顺序：

### 2.1 核心框架

| 库 | 版本 | 负责什么 | 在本项目哪里用到 |
|---|---|---|---|
| **Spring Boot** | 4.0.3 | 整个应用的地基：自动配置、内嵌 Tomcat、启动入口 | `ZhihuiqingtuApplication.java` |
| **Java** | 17 | 语言版本 | `pom.xml:30` |
| **spring-boot-starter-webmvc** | (随 Boot) | HTTP 接口层：`@RestController`、`@GetMapping`、请求参数绑定、内嵌 Tomcat | 6 个 Controller 全部 |
| **spring-boot-starter-validation** | (随 Boot) | 参数校验：`@NotBlank`、`@Size`、`@NotNull` 等注解的运行时支持 | `dto/` 下所有请求体类 |

> **注意 Boot 4 的一个大坑**：Boot 4 用的 JSON 库是 **Jackson 3**，包名是 `tools.jackson.*`。
> 网上 99% 的 Jackson 教程讲的是 Jackson 2（`com.fasterxml.jackson.*`），**照抄会编译不过**。
> 本项目里 Jackson 2 只作为 `jjwt-jackson` 的运行时依赖存在，编译期引用不到。

### 2.2 数据持久层

| 库 | 版本 | 负责什么 | 在本项目哪里用到 |
|---|---|---|---|
| **MyBatis-Plus** | 3.5.15 | 数据库操作。**不用写 SQL** —— 继承 `BaseMapper<T>` 就自带增删改查 | `repository/` 下 9 个接口 |
| **mybatis-plus-jsqlparser** | 3.5.15 | 分页插件和防全表更新插件的 SQL 解析引擎 | `config/MybatisPlusConfig.java` |
| **mysql-connector-j** | (随 Boot) | JDBC 驱动，Java 连 MySQL 的"电话线" | `application.properties:7` |

MyBatis-Plus 在本项目实际用到的 6 个能力：

1. **`BaseMapper<T>`** — 零 SQL 的基础 CRUD。例：`ActivityMainRepository extends BaseMapper<ActivityMain>`
2. **`LambdaQueryWrapper`** — 用 Java 方法引用拼查询条件，例：`wrapper.eq(ActivityMain::getPublisherUserId, userId)`
3. **`PaginationInnerInterceptor`** — 分页插件，把 `LIMIT` 自动拼进 SQL
4. **`BlockAttackInnerInterceptor`** — 防全表更新/删除的保险丝（拦住忘写 `WHERE` 的 `UPDATE`）
5. **`MetaObjectHandler`** — 自动填充 `createTime` / `updateTime`，不用每次手写
6. **`@TableLogic`** — **逻辑删除**。调 `deleteById` 不会真删行，而是把 `delete_flag` 置 1

> **逻辑删除是本项目贯穿全局的设计**：每张表都有 `delete_flag`（0=未删 1=已删），
> 并且**所有唯一索引都把 `delete_flag` 拼进去了**（如 `uk_activity_enroll_user (user_id, activity_id, delete_flag)`）。
> 这样"删了再建同名记录"不会被唯一索引拦住 —— 这是个很实用的技巧。

| 库 | 版本 | 负责什么 | 在本项目哪里用到 |

> ✅ **重要现状（2026-09-20 更新）**：Redis **已经真正用起来了**，共 6 个场景。

### 2.4 安全

| 库 | 版本 | 负责什么 | 在本项目哪里用到 |
|---|---|---|---|
| **jjwt** (api/impl/jackson) | 0.12.6 | 签发和解析 JWT 令牌（HS256 算法） | `common/JwtUtil.java` |
| **spring-security-crypto** | (随 Boot) | **只为了 `BCryptPasswordEncoder` 这一个类**，用来做密码哈希 | `config/PasswordConfig.java` |
| **spring-boot-starter-actuator** | (随 Boot) | 健康检查端点 `/actuator/health` 等 | 未额外配置 |

**为什么密码要用 BCrypt 而不是 MD5/SHA？**

- MD5/SHA 是"快"的哈希 —— 快对攻击者是好事，一秒能试几十亿次密码。
- BCrypt 故意设计得**慢**（本项目 cost=10，每次哈希约 100ms），暴力破解成本极高。
- BCrypt 把**随机盐明文打包进密文**（形如 `$2a$10$SDu2ky7...`，共 60 字符），
  所以**数据库不需要额外的 salt 列**，`password_hash VARCHAR(255)` 就够。

**为什么刻意不引 `spring-boot-starter-security`？**

见 `pom.xml:51-55` 的注释：那个 starter 会自动给所有接口套上登录校验，
而本项目自己用 JWT 拦截器管鉴权，两套机制会打架。所以**只引纯工具库 `spring-security-crypto`**。

## 3. 代码分层：一个请求的完整旅程

初学者最该先搞懂的就是这个。以"发布一个活动"为例，请求从进来到落库经过 6 层：

```
① 浏览器  POST /api/activities  {JSON 请求体}
        │
        ▼
② TokenInterceptor          ← 拦截器：校验请求头里的 token，不合法直接 401
        │  (interceptor/TokenInterceptor.java)
        ▼
③ ActivityController        ← 控制器：只做"接参数、调服务、包结果"，不写业务
        │  (@RequestBody CreateActivityRequest → 自动 JSON 反序列化 + @Valid 校验)
        ▼
④ ActivityServiceImpl       ← 服务层：真正的业务规则都在这里
        │  (@Transactional 开事务，校验发布权限、校验学分规则、拼实体)
        ▼
⑤ ActivityMainRepository    ← 仓库层：继承 BaseMapper，不写 SQL
        │  (insert(activityMain))
        ▼
⑥ MySQL  activity_main 表   ← 数据最终落到这里
```

**每层的职责边界（很重要）**：

| 层 | 包 | 只该干什么 |
|---|---|---|
| Controller | `controller/` | 接参数、调 Service、返回 `ApiResponse`。**不写 if-else 业务判断** |
| Service | `service/` + `service/impl/` | 业务规则、事务、多个 Repository 的编排 |
| Repository | `repository/` | 只跟数据库打交道，继承 `BaseMapper` 即可 |
| Entity | `entity/` | 和数据库表**一一对应**的类，一个字段对一列 |
| DTO | `dto/` | **接收**前端传来的请求体（如 `CreateActivityRequest`） |
| VO | `vo/` | **返回**给前端的视图对象（如 `ActivityResponse`），字段可以和表不一样 |

> **DTO 和 Entity 为什么要分开？** 因为"前端能传的字段"和"表里有的列"不是一回事。
> 比如 `CreateActivityRequest` 里没有 `activityId`（新建时还不存在）、没有 `currentParticipant`
> （由系统算），如果直接用 Entity 接参数，客户端就能伪造这些字段。**分开是安全设计，不是啰嗦。**

## 4. 数据库：10 张表逐张讲

数据库名 `campus_activity_platform`，MySQL 8.0.44。

> ⚠️ **一个需要注意的差异**：`src/main/resources/Mysql.sql` 里只定义了 **9 张表**，
> 但实际数据库里有 **10 张** —— 多出来的是 `recommend_log`。
> 它是已删除的"AI 推荐模块"留下的残留表（对应的 Java 代码 `RecommendLog.java`、`RecommendationService.java`
> 等在 git 里已标记为删除）。**业务上已经没有任何代码在用它。**

### 4.1 用户域

#### `user_info` — 用户表（主键是学号，不是自增 ID）

| 列 | 类型 | 说明 |
|---|---|---|
| `student_no` | VARCHAR(20) | **主键**。学号或工号，如 `20210001`、`T0001` |
| `user_name` | VARCHAR(50) | 姓名 |
| `user_phone` | VARCHAR(20) | 手机号，唯一 |
| `user_email` | VARCHAR(100) | 邮箱，唯一 |
| `user_role` | TINYINT | 角色：**1=学生 2=管理员 3=老师**，默认 1 |
| `publisher_status` | TINYINT | 发布资格：**0=未开通 1=已开通**，默认 0 |
| `major` | VARCHAR(100) | 专业 |
| `grade` | VARCHAR(20) | 年级 |
| `password_hash` | VARCHAR(255) | BCrypt 密文（60 字符） |

**为什么主键用学号而不是自增 ID？**
因为学号本身就是**业务唯一标识**，天然唯一、有含义、长度可控。
其他表引用用户时统一存 `VARCHAR(20)` 的学号（如 `publisher_user_id`、`user_id`），
好处是查数据时一眼能看懂是谁，不用来回 JOIN 转 ID。

**`user_role` 和 `publisher_status` 是两个独立概念**：
- `user_role` 是**身份**（你是学生还是老师）
- `publisher_status` 是**权限**（你有没有资格发活动）

设计上允许"普通学生也能发活动"（只要管理员给他开了发布资格），这在实际校园场景里很常见。

### 4.2 活动域

#### `activity_main` — 活动主表（本项目最核心的表）

| 列 | 类型 | 说明 |
|---|---|---|
| `activity_id` | BIGINT UNSIGNED | 主键，自增 |
| `publisher_user_id` | VARCHAR(20) | 发布人学号 |
| `activity_title` | VARCHAR(255) | 活动标题 |
| `activity_desc` | TEXT | 活动详情 |
| `activity_type` | TINYINT | **活动类型：1=第二课堂学分 2=志愿服务 3=运动健身 4=兴趣团建** |
| `activity_credit` | DECIMAL(5,2) | 学分，**仅类型 1 使用** |
| `credit_type` | TINYINT | 学分类型 1~6，**仅类型 1 使用** |
| `volunteer_hours` | DECIMAL(6,2) | 志愿时长，**仅类型 2 使用** |
| `cover_url` | VARCHAR(500) | 封面图地址 |
| `start_time` / `end_time` | DATETIME | 活动起止时间 |
| `activity_location` | VARCHAR(255) | 地点 |
| `max_participant` | INT UNSIGNED | 人数上限，**0 表示不限** |
| `current_participant` | INT UNSIGNED | 当前报名人数（**冗余计数器**） |
| `activity_status` | TINYINT | **库里只存 1=已发布 4=已取消** |
| `sign_in_enabled` | TINYINT | 签到开关：0=关闭 1=开启 |

**三个关键设计点，初学者最容易踩坑：**

**① 活动类型决定了哪些字段有值** —— 这是本项目的核心业务规则：

| 活动类型 | 学分 | 学分类型 | 志愿时长 |
|---|---|---|---|
| 1 第二课堂学分 | ✅ 必填，且必须是 **0.05 的倍数** | ✅ 必填 | ❌ 禁止设置 |
| 2 志愿服务 | ❌ 禁止 | ❌ 禁止 | ✅ 必填 |
| 3 运动健身 | ❌ 禁止 | ❌ 禁止 | ❌ 禁止 |
| 4 兴趣团建 | ❌ 禁止 | ❌ 禁止 | ❌ 禁止 |

违反这些规则会返回 400（参数不合法），具体原因见 message。校验逻辑在 `ActivityServiceImpl` 里。
"0.05 的倍数"这条由自定义注解 `@CreditUnit` + `CreditUnitValidator` 实现（`validation/` 包）。

**② `activity_status` 里没有"已结束(3)"** —— 这是全项目最反直觉的一点。

数据库里**永远不会存 3**。用户看到的"已结束"是**查询时现算的**：

```java
// ActivityStatusEnum.resolveDisplayStatus()
if (endTime != null && !endTime.isAfter(LocalDateTime.now())) {
    return FINISHED.code;   // 3
}
```

也就是拿 `end_time` 和当前时间比一下。这么做的好处是**不需要定时任务去刷状态**。
所以你会看到两个不同的状态字段：`activityStatus`（数据库真值）和 `displayStatus`（前端展示值）。

> 这个设计有个重要推论：**不要把活动状态缓存进 Redis**。
> 缓存 1 小时的话，10:00 结束的活动在 10:00~11:00 会一直显示"进行中"，
> 而且数据库和代码都是对的，只有缓存是错的 —— 极难排查。

**③ `current_participant` 是冗余计数器**，不是实时 `COUNT(*)` 出来的。
好处是列表页不用每条活动都去数一遍报名记录；代价是**必须保证它和真实记录数一致**。

#### `activity_tag` — 活动标签字典（6 条数据）

`tag_id` / `tag_name` / `tag_desc`。项目启动时会自动初始化（`config/ActivityTagDataInitializer.java`）。

#### `activity_tag_rel` — 活动↔标签关联表（多对多）

`activity_id` + `tag_id`，唯一键 `uk_activity_tag_rel (activity_id, tag_id, delete_flag)`。

**当前 0 行数据。**

### 4.3 报名域

#### `activity_enroll` — 报名记录表（17 行数据，是当前最"活"的表）

| 列 | 类型 | 说明 |
|---|---|---|
| `enroll_id` | BIGINT UNSIGNED | 主键 |
| `user_id` | VARCHAR(20) | 报名人学号 |
| `activity_id` | BIGINT UNSIGNED | 活动 ID |
| `enroll_status` | TINYINT | **1=已报名 3=已签到 4=已完成** |
| `sign_in_time` | DATETIME | 签到时间 |
| `sign_out_time` | DATETIME | 签退时间 |
| `feedback_score` | TINYINT UNSIGNED | 评价分数 |
| `feedback_content` | VARCHAR(500) | 评价内容 |

**唯一键 `uk_activity_enroll_user (user_id, activity_id, delete_flag)`** —— 数据库层面拦住重复报名。
**外键 `fk_activity_enroll_activity`** 指向 `activity_main`，`fk_activity_enroll_user` 指向 `user_info(student_no)`。

> **外键的意义**：如果你用不存在的学号报名，数据库会直接拒绝插入。
> 这也是为什么测试脚本 `docs/api-test/seed-users.mjs` 必须**先批量注册用户**才能测报名。

**状态机**：

```
ENROLLED(1)  ──签到──▶  SIGNED_IN(3)  ──签退──▶  COMPLETED(4)
   已报名                  已签到                    已完成
```

> 发布者/管理员可以补签到、补签退、撤销签到、撤销签退；
> 撤销签退时会回滚尚未确认的发放记录，已发放的记录需先改为「不发放」。

### 4.4 学分域

#### `credit_record` — 学分/时长发放记录表（当前 0 行）

| 列 | 类型 | 说明 |
|---|---|---|
| `record_id` | BIGINT UNSIGNED | 主键 |
| `user_id` | VARCHAR(20) | 学生学号 |
| `activity_id` | BIGINT UNSIGNED | 来源活动 |
| `credit` | DECIMAL(5,2) | 发放学分；志愿时长记录为 0 |
| `credit_type` | TINYINT NULL | 1~6（创新创业/智育/德育/体育/美育/劳育）；志愿时长记录为空 |
| `volunteer_hours` | DECIMAL(6,2) NULL | 发放的志愿时长（志愿活动） |
| `verify_user_id` | VARCHAR(20) | 确认人（发布者/管理员）学号 |
| `verify_status` | TINYINT | **0=待确认 1=已发放 2=不发放 3=待管理员审核（灵活志愿）** |
| `reject_reason` | VARCHAR(255) | 不发放原因 |
| `verify_time` | DATETIME | 确认/调整时间 |

**这张表为什么需要"确认"这一环？**
因为学分/时长是**有公信力的凭证**，不能学生自己说拿到就拿到。
流程是：学生**签退**成功 → 系统**自动**插入一条 `verify_status=0` 的记录 →
活动发布者在「参与人员」中按人调整金额并确认 → 改成 1 或 2。
**只有 1 的记录才算真正拿到学分/时长，也才计入统计。**

**谁能确认发放？**
- 活动的发布者本人（包括运营人员发布的活动）
- 管理员（拥有发布者的全部权限）

两者都可以修正考勤、修改每人的学分数/学分类型/志愿时长，并确认是否发放。
同一活动不同参与者可以拿到不同金额；撤销签退时未确认的记录会被物理删除，
已发放的记录需先改为「不发放」才能撤销签退。

## 6. 核心业务流程

### 6.1 注册与登录

```
注册  POST /api/auth/register
  ├─ 校验学号/手机号/邮箱是否已存在 → 409 / 409 / 409
  ├─ 密码 BCrypt 加密（AuthServiceImpl.java:63）
  └─ 落库 user_info

登录  POST /api/auth/login
  ├─ 按学号查用户 → 查不到返回 404 "用户不存在"
  ├─ passwordEncoder.matches(明文, 密文) → 不匹配返回 400
  └─ JwtUtil 签发 token（有效期 12 小时 = 43200000ms）
```

**JWT 是什么？** 一个"签了名的身份证"。服务端用自己的密钥（`jwt.secret`）签名，
客户端把 token 存下来，之后每次请求都带上。服务端验签就知道"这确实是我发的，且没过期"。
好处是**服务端不用存 session**，天生适合前后端分离。

> `jwt.secret` 必须 **≥32 字节**（HS256 要求），配置在 `application.properties:33`，
> 支持用环境变量 `JWT_SECRET` 覆盖。

**登录返回体**（`LoginResponse`）：token + 用户基本信息 + 角色 + 发布资格。

### 6.2 发布活动（含封面）

```
POST /api/activities/covers   先传封面图 → 返回 coverUrl（413 超 5MB / 400 非图片格式）
POST /api/activities          再建活动
  ├─ 校验发布资格（publisher_status）→ 403
  ├─ 校验活动类型对应的字段规则 → 400（字段互斥，具体原因见 message）
  ├─ 校验 end_time > start_time → 400
  ├─ 校验标签 ID 是否存在 → 400
  └─ 落库 activity_main + activity_tag_rel
```

上传的图片存在 `campus.upload.base-dir`（默认 `${user.dir}/uploads`），
通过 `StaticResourceConfig` 映射到 `/uploads/**` 供前端 `<img src>` 直接访问。

### 6.3 报名 → 签到 → 评价 → 学分（**本项目最核心的闭环**）

```
① 报名  POST /api/enrollments
   ├─ 活动是否存在 → 404
   ├─ 活动状态是否可报名 → 409 / 409
   ├─ 人数是否已满 → 409
   ├─ 是否重复报名 → 409
   ├─ 插入 activity_enroll（状态 1）
   └─ activity_main.current_participant + 1

② 签到  PATCH /api/enrollments/{enrollId}/sign-in
   ├─ 必须是自己的报名记录 → 403
   ├─ 活动必须已开启签到开关 → 409
   ├─ 已结束/已取消活动不能签到 → 409
   ├─ 状态从 1 改为 4，写入 sign_in_time
   └─ ★ 触发学分生成（见下）

③ 评价  PATCH /api/enrollments/{enrollId}/feedback
   ├─ 必须已完成签到 → 409
   └─ 写入 feedback_score + feedback_content

④ 学分生成（自动，EnrollmentServiceImpl.java:163-180）
   └─ 仅当 activity_type = 1（第二课堂学分活动）时，
      自动插入 credit_record，verify_status = 0（待审核）

⑤ 学分审核  PATCH /api/credits/{recordId}/review
   ├─ 权限校验：管理员/老师任意，学生只能审自己发布的活动 → 403
   └─ verify_status 改为 1（通过）或 2（驳回，需填 reject_reason）
```

> **为什么只有"第二课堂学分活动"才生成学分记录？**
> 因为志愿服务算的是"志愿时长"，运动健身和兴趣团建是纯活动，都不走学分体系。
> 这是校园场景的真实业务规则。

### 6.4 组队流程

```
建队    POST /api/teams                     → team_status=0 招募中，创建者自动成为队长
申请    POST /api/teams/{id}/join           → team_member 状态 0 待审核（409 重复申请）
审核    PATCH /api/teams/{id}/members/{mid}/review  → 1 已加入 / 2 已驳回（仅队长，403）
                                                     → current_size + 1，满员则 team_status=1
退出    PATCH /api/teams/{id}/members/{mid}/exit    → 状态 3，current_size - 1
                                                     队长不能退出 → 409
解散    PATCH /api/teams/{id}/dismiss               → team_status=2（仅队长，403）
```

### 6.5 删除活动的级联清理

`DELETE /api/activities/{activityId}` 不只是删活动本身，还会**级联清理**：
标签关联（`activity_tag_rel`）、报名记录（`activity_enroll`）、学分记录（`credit_record`）、
组队数据（`team_main` / `team_member`）。

所谓"删除"全是**逻辑删除**（`delete_flag = 1`），数据行还在，只是查不到了。

## 8. 统一约定

### 8.1 响应格式 `ApiResponse<T>`

**所有**接口（成功和失败）都返回同一个结构：

```json
{
  "code": 0,
  "message": "success",
  "data": { ... }
}
```

- **`code = 0` 表示成功**，非 0 一律是失败。
- `data` 是具体业务数据，失败时为 `null`。

### 8.2 分页 `PageResponse<T>`

```json
{
  "content": [ ... ],
  "page": 0,
  "size": 10,
  "totalElements": 37,
  "totalPages": 4
}
```

> ⚠️ **页码基准被转换过**：MyBatis-Plus 内部页码从 **1** 开始，
> 但 `PageResponse` 对外统一暴露成从 **0** 开始（前端习惯）。
> 转换逻辑在 `common/PageResponse.java`。

### 8.3 错误码

**业务码与 HTTP 状态码同值**（成功为 0），取值集中在 `common/ErrorCode.java`，
不再按业务模块分段：

| 码 | 含义 | 例子 |
|---|---|---|
| **0** | 成功 | — |
| **400** | 参数不合法 | DTO 校验失败、JSON 格式错、活动类型字段互斥校验、时间区间非法 |
| **401** | 未认证 | 未带令牌、令牌无效或过期、令牌已登出 |
| **403** | 无权限 | 无发布权限、无活动管理权限、非本人操作、仅队长可审核 |
| **404** | 资源不存在 | 活动/报名/队伍/队员/学分记录/用户不存在 |
| **409** | 状态冲突 | 学号已存在、人数已满、重复报名、已结束不可报名、队伍已满 |
| **413** | 请求过大 | 封面超过 5MB |
| **429** | 请求过频 | 登录失败次数过多 |
| **500** | 系统内部异常 | 兜底 |

> 多个具体原因归入同一码（例如"人数已满"与"重复报名"同为 409），
> 区分具体原因由 `message` 承担。完整对照见 `docs/错误码对照表.md`。
>
> 这是 2026-10-11 的改造结果：此前错误码是自定义 4 位分段码（如 409 人数已满），
> 且业务错误一律返回 HTTP 200。现在业务码取 HTTP 语义值，HTTP 状态码与之保持一致，
> 访问日志、网关与监控可以直接按标准 HTTP 语义统计。

### 8.4 鉴权方式

除登录、注册、上传图片、接口文档外，**所有请求都要在 Header 里带 token**：

```
token: eyJhbGciOiJIUzI1NiJ9...
```

不带或过期 → 拦截器直接返回 `401` + `{"code":401,"message":"未登录，请先登录"}`。

## 10. 现状提醒（读代码时要知道的事）

以下是当前代码的**真实状态**，不是建议 —— 你读代码时会撞见，提前知道能少走弯路。

### 10.1 鉴权是"半成品"

- **前端从来没发过 token**。三个前端目录（`frontend/`、`frontend_v2/`、`static/`）里
  搜 `token` **零命中**，`http.js` 只有响应拦截器、没有请求拦截器。
  由于 `TokenInterceptor` 要求 `token` 请求头，**除登录注册外，所有前端 API 调用都会 401**。
- **`TokenInterceptor.java:65` 用 `url.contains("/login")` 做免鉴权判断**，
  这是**字符串包含**而不是路径匹配。实测 `/api/users/login` 能绕过鉴权直接进控制器。
- **`WebConfig.java:23` 的排除路径写的是 `/user/login`、`/user/register`**，
  但实际路径是 `/api/auth/login`、`/api/auth/register` —— **对不上**。
  功能上目前只靠上面那个 `contains` 兜住。
- **权限判定基于请求体里自报的 `userId`**，而不是 token 里的身份。
  `JwtUtil.getRole()` 实现了但**全项目零调用**。也就是说：**改个请求体里的 userId 就能操作别人的数据。**

### 10.2 报名并发：曾超卖 + 曾死锁 —— **已修复**（2026-09-20）

**修复前的状态**（保留在这里，因为它是个很好的教学案例）：

`EnrollmentServiceImpl.createEnrollment` 是典型的 **check-then-act**：
先读人数判断、再插入、再回写计数器，**中间没有任何锁**。
并发下两个请求都读到"还剩 1 个名额"，结果报名记录多出一条。
更隐蔽的是：**超卖时 `current_participant` 看起来完全正常**（两个事务都写回同一个值），
必须去数 `activity_enroll` 的记录数才能发现。

同时它还会**触发 MySQL 死锁**：`activity_enroll` 的外键让 INSERT 在父表 `activity_main` 上加 S 锁，
随后 `updateById` 又要 X 锁，两个事务各持 S 锁互等 → 循环等待。

**实测基线**：21 个并发请求 → 成功 2 个、报名记录 6 条（上限 5）、8 次死锁。

**修复方式（两处，且完全没用到 Redis）**：

1. `ActivityMainRepository` 新增 `tryOccupySeat` / `releaseSeat` 两条**原子 SQL**
   （把"判断名额"压进 `UPDATE ... WHERE current_participant < max_participant`，
   从**快照读**变成**当前读**）；
2. 把这条 `UPDATE` **提到 INSERT 报名记录之前** —— 这一步同时解决超卖和死锁
   （先拿排他锁，再做外键插入）。

**修复后实测**：成功 1 个、报名记录 5 条、死锁 0 次，连续 8 次一致。
之后又叠加了 Redis 库存闸门作为性能层（`activity:stock:{id}`），
但**正确性来自数据库，不来自 Redis**。
